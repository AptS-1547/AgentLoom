# 本地推理缓存与视觉-对话优化方案（草案）

> 状态：设计讨论阶段，部分思路待推敲

## 1. 问题背景

本地 Qwen2.5-VL-3B 的约束：
- **上下文窗口小**（4K token），无法放入完整对话历史
- **时序能力差**，连续多轮对话容易丢失前文信息
- **推理成本高**（~3.8s/次），相似场景重复推理浪费算力和 VRAM
- **视觉→对话对接**信息损失大，高度抽象的文本 summary 丢失大量视觉细节

三个优化方向：视觉缓存、对话压缩缓存、结构化视觉描述。

## 2. 视觉缓存系统

### 2.1 核心思路

利用 ViT embedding 的帧间余弦相似度做缓存检索，相似场景直接命中缓存，跳过 VLM 推理。

```
新帧 → ViT embedding → 余弦相似度检索缓存
  ├─ 相似度 > 阈值高 → 直接返回缓存描述（~1ms）
  ├─ 相似度 中间区间 → 返回缓存 + 标注"场景相似但有变化"
  └─ 相似度 < 阈值低 → 执行 VLM 推理（~3.8s）→ 写入缓存
```

### 2.2 缓存结构

```cpp
struct VisualCacheEntry {
    std::vector<float> embedding;    // ViT embedding（用于相似度检索）
    std::string description;         // VLM 生成的描述
    std::string scene;               // 场景概括
    std::vector<std::string> facts;  // 可观察事实
    int64_t timestamp_ms;            // 写入时间
    int hit_count;                   // 命中次数
};
```

### 2.3 待推敲的问题

**阈值设定**：
- 相似度阈值需要实测数据标定
- 不同场景（室内静态 vs 户外动态）可能需要不同阈值
- 是否需要自适应阈值？

**缓存淘汰策略**：
- LRU？LFU？时间衰减？
- 缓存大小如何限制（VRAM 中存 embedding 向量的开销）
- 场景切换时是否需要清空缓存？

**语义漂移**：
- 两帧 ViT embedding 相似度高，但语义上下文可能不同
  - 例：用户坐在同一张桌子前，但情绪从开心变为沮丧
  - ViT 看到的像素级变化很小，但语义差异大
- 是否需要结合情绪状态机的输出做联合判断？

**缓存一致性**：
- 缓存的描述是某一时刻的快照，随时间推移可能过时
- 需要 TTL（生存时间）机制？还是在上下文变化时主动失效？

### 2.4 预期收益

看板娘/QQ 场景下，用户长时间坐在同一位置：
- 缓存命中率预估 70-90%
- VLM 推理调用减少 70-90%
- 事件检测响应时间从 ~4s 降到 ~20ms（缓存命中时）

## 3. 对话压缩缓存

### 3.1 核心思路

3B 模型 4K 上下文放不下完整对话。用滑动窗口 + 增量压缩：

```
对话历史（原文）→ 超过阈值时触发压缩
  ├─ 最近 N 轮保留原文（工作记忆）
  └─ 更早的轮次 → 本地 VLM 生成 summary → 缓存
```

推理时的 prompt 结构：

```
[system prompt]
[cached_summary: 之前对话的压缩摘要]
[recent_turns: 最近 N 轮原文]
[visual_context: 当前视觉状态]
[current_input: 用户输入]
```

### 3.2 压缩策略

**触发时机**：
- 当 prompt 总 token 数超过 `context_window * 0.6` 时触发
- 压缩最早的 M 轮对话为 summary

**压缩方式**：
- 用本地 VLM 自身生成 summary（不依赖云端）
- prompt 模板："请将以下对话压缩为简短摘要，保留关键信息和情感状态"
- 压缩后的 summary 缓存到内存/磁盘

**增量压缩**：
- 不是每次都重新压缩全部历史
- 新的 summary = 旧 summary + 新增对话 → 再压缩
- 避免压缩链过长导致信息丢失

### 3.3 与主项目记忆系统的关系

主项目（MyNeuroLikeSystem）已有 L1-L4 分级记忆：
- L1: 工作记忆（当前对话原文）
- L2: 会话摘要
- L3: 长期向量记忆（Qdrant）
- L4: 知识库

本地 VLM 的对话压缩缓存对应 **L1 → L2 的压缩路径**，但在推理端本地完成，不依赖主项目的 Python 记忆管理器。

### 3.4 待推敲的问题

**压缩质量**：
- 3B 模型的摘要能力是否足够？
- 压缩后是否丢失关键信息（特别是情感细节）？
- 需要实测对比：3B 摘要 vs 7B 摘要 vs 云端摘要

**与主项目的一致性**：
- 推理端的压缩缓存和主项目的 memory_manager 是否会冲突？
- 两者的 summary 格式是否需要统一？
- 还是推理端只做临时压缩，长期记忆仍由主项目管理？

**token 预算分配**：
- 4K context 中 system prompt 占多少？
- summary 允许占多少 token？
- 留给当前推理的空间有多少？
- 需要实测不同分配比例对输出质量的影响

## 4. 结构化视觉描述（替代高度抽象的 summary）

### 4.1 当前问题

视觉链路和主聊天 LLM 对接时信息损失大：

```
当前路径：
  图片 → 本地 VLM → "用户在看书"（50 字摘要）→ 云端 Claude
  问题：Claude 只看到一句话，丢失了空间关系、物体细节、动作序列
```

### 4.2 改进方案

本地 VLM 输出分层结构化信息，而不是一句话 summary：

```json
{
  "scene": "书桌前",
  "objects": [
    {"name": "笔记本电脑", "position": "桌面中央", "state": "打开"},
    {"name": "咖啡杯", "position": "右手边", "state": "半满"},
    {"name": "书", "position": "左手边", "state": "翻开"}
  ],
  "subject": {
    "posture": "坐姿",
    "gaze": "看向屏幕",
    "hands": "双手放在键盘上"
  },
  "actions": ["正在打字", "偶尔看向书本"],
  "changes_from_previous": ["咖啡杯从满变为半满", "书翻了几页"]
}
```

这比"用户在看书"信息量大得多，但 token 成本仍然可控（~100 token vs 图片的 1350 vision token）。

### 4.3 ViT token 直传云端的可行性分析

理想方案：将本地 ViT 的 token 直接作为云端 API 的输入。

**障碍**：
- Qwen2.5-VL 的 ViT 和 Claude/GLM 的 vision encoder 是不同的模型
- Embedding 空间不兼容，不能直接互通
- 云端 API 通常只接受图片二进制数据或 base64，不接受裸 embedding

**替代方案**：
- 本地 VLM 生成结构化描述（方案 4.2）
- 仅在需要高精度分析时才传原始图片给云端
- 用描述质量的置信度决定是否需要云端兜底

### 4.4 本地 VLM 作为视觉预处理器

```
新的对接方式：
  图片 → 本地 ViT（事件检测）
       → 本地 VLM（结构化描述，~100 token）
       → 云端 Claude（拿到结构化描述 + 对话上下文）

  需要云端精确分析时：
  图片 → 本地 ViT（事件检测）
       → 直接传原始图片给云端（base64）
       → 云端 Claude（直接看图）
```

本地 VLM 充当"视觉预处理器"，日常场景用结构化描述（省 token），复杂场景 fallback 到原图传云端。

### 4.5 待推敲的问题

**结构化描述的 prompt 工程**：
- 3B 模型能否稳定输出 JSON 格式？
- 是否需要约束输出格式（grammar-constrained generation）？
- llama.cpp 支持 GBNF grammar，可以强制 JSON 输出

**云端何时介入**：
- 置信度如何度量？本地 VLM 没有显式的置信度输出
- 是否用 ViT embedding 的异常检测（与历史分布的偏离程度）？
- 或者简单规则：描述中出现"不确定"/"可能"关键词时 fallback？

**LoRA 微调路径**：
- 收集本地 VLM 的结构化描述 + 云端 Claude 的修正
- 用修正数据 LoRA 微调本地模型
- 逐步降低云端调用率

## 5. 三个方向的依赖关系

```
视觉缓存（独立，可先做）
  ↓ 提供 embedding 基础设施
结构化视觉描述（依赖视觉缓存的 embedding）
  ↓ 提供 summary 生成能力
对话压缩缓存（可独立做，但与视觉描述共享压缩逻辑）
```

建议实施顺序：
1. 视觉缓存（收益最直接，减少 70-90% 推理调用）
2. 结构化视觉描述（改善云端对接质量）
3. 对话压缩缓存（解决上下文窗口限制）

## 6. 开放问题

1. **缓存存储**：纯内存还是持久化到磁盘？跨 session 是否保留？
2. **多模态缓存键**：图片 + 文本 prompt 联合作为缓存键，还是只用图片 embedding？
3. **缓存预热**：启动时是否从磁盘加载历史 embedding？
4. **与 Qdrant 的关系**：主项目已有 Qdrant 做向量检索（L3 记忆），视觉缓存是否复用同一套向量数据库？
5. **量化 embedding**：ViT embedding 是否需要量化以节省内存？（int8 量化可减少 4x 存储）
6. **批量处理**：视频流场景下，是否可以批量编码多帧然后批量检索缓存？

## 2. 流媒体连接池设计

### 2.1 专用连接池架构

**设计要点**：
- **独立 io_context**：流媒体连接与 HTTP 请求隔离，避免相互阻塞
- **专用线程池**：2-4 个 IO 线程处理 WebSocket 协议，8-16 个计算线程处理帧分析
- **Bounded 队列**：帧队列上限 5-10 帧，防止解码速度超过处理速度时内存膨胀
- **背压机制**：队列满时丢弃旧帧，保证实时性

### 2.2 连接生命周期

```text
客户端连接
  │
  ├─> WebSocket 握手 (HTTP Upgrade)
  ├─> 验证 session_id / user_uuid
  ├─> 创建 WebSocketSession
  │     └─> 绑定到 io_context (round-robin)
  │
  ├─> 进入帧接收循环
  │     ├─> async_read (binary frame)
  │     ├─> 解码 (JPEG/H.264)
  │     ├─> 推入 frame_queue
  │     └─> 继续 async_read
  │
  └─> 连接关闭
        ├─> 清理 session
        ├─> 刷新未处理帧
        └─> 释放资源
```

## 3. 帧处理流水线

### 3.1 多线程生产者-消费者模式

```
┌──────────────┐      ┌──────────────┐      ┌──────────────┐
│  IO Thread   │      │  Detector    │      │  Selector    │
│  (Producer)  │ ───> │  Thread      │ ───> │  Thread      │
│              │      │  (Consumer)  │      │  (Consumer)  │
└──────────────┘      └──────────────┘      └──────────────┘
       │                     │                     │
       │ frame_queue         │ event_buffer        │ key_frames
       │ (bounded)           │ (1s window)         │ (batch)
       │                     │                     │
       ▼                     ▼                     ▼
  WebSocket 接收        MOG2 + 三信号融合      峰值检测 + VLM 调用
```

### 3.2 帧差与事件检测

**核心算法**：MOG2 自适应背景模型

**三信号融合**：
- **S1：前景面积占比** (权重 0.5) - 多大区域在变化
- **S2：灰度直方图距离** (权重 0.2) - 全局场景切换
- **S3：边缘密度变化率** (权重 0.3) - 结构性变化

**性能优化**：
- 预处理：5×5 高斯模糊去噪
- 形态学操作：3×3 腐蚀 + 膨胀
- 连通域过滤：面积 < 0.5% 画面的区域忽略
- 时域投票：连续 3 帧中至少 2 帧触发才认定为有效事件

### 3.3 关键帧筛选

**峰值检测算法**：
- 时域平滑：指数移动平均 (EMA)，α = 0.3
- **FFT 频域分析**：对融合信号进行 FFT 变换，识别主导频率分量，按频率峰值做自适应采样（避免固定窗口对快/慢变化场景的偏差）
- 局部极大值检测：在 1 秒滑动窗口内寻找峰值（窗口大小根据 FFT 主频自适应调整）
- 清晰度优选：峰值区间内选择拉普拉斯方差最大的帧
- 冷却间隔：0.5 秒，避免连续提交相似帧

**FFT 自适应采样原理**：
- 高频场景（如快速动作）→ 缩短采样窗口，提高响应速度
- 低频场景（如静态学习）→ 延长采样窗口，减少 VLM 调用
- 主频识别帮助过滤周期性噪声（如风扇、灯光闪烁）

## 4. 全局计算线程池

### 4.1 线程池设计

**任务类型**：
- FRAME_DETECTION：MOG2 + 三信号融合
- VECTOR_SIMILARITY：Faiss 向量匹配
- TOP_K_SEARCH：SIMD Top-K 搜索
- OPENCV_FILTER：形态学 + 边缘检测

**任务调度策略**：
- **优先级队列**：VLM 推理 > 向量搜索 > 帧检测
- **批处理优化**：累积 4-8 个关键帧后批量调用 VLM
- **负载均衡**：Round-robin 分配任务到空闲线程
- **背压控制**：队列满时丢弃低优先级任务

### 4.2 计算密集型任务性能

| 任务类型 | 平均延迟 | 吞吐量 | SIMD 优化 |
|---------|---------|--------|----------|
| MOG2 背景减除 | 1-3 ms | 333-1000 fps | ✅ (OpenCV 内置) |
| 三信号融合 | 0.1 ms | 10K ops/sec | ✅ (AVX2) |
| 向量相似度 (384 dim) | 0.02 µs | 50M ops/sec | ✅ (AVX2 FMA) |
| Top-K 搜索 (10K 记录) | 0.03 ms | 33K ops/sec | ✅ (partial_sort) |
| 拉普拉斯清晰度 | 0.5 ms | 2K fps | ✅ (OpenCV SIMD) |

## 5. VLM 推理集成

### 5.1 异步 gRPC 调用

**批量推理优化**：
- 累积 4-8 个关键帧后批量调用 VLM
- 单帧延迟从 2s 降至 0.5s
- 使用异步 gRPC，不阻塞帧检测线程

### 5.2 VLM 输出结构

三层结构化输出：
1. **事实层**：客观描述画面内容（置信度 >0.9）
2. **弱解释层**：可能的行为意图（置信度 0.7-0.8）
3. **记忆候选层**：值得记录的稳定行为模式（置信度 0.6-0.7）

**示例**：
- 事实层："用户坐在书桌前，面前有一本打开的书"
- 弱解释层："可能在阅读或学习"
- 记忆候选层："用户在书桌前持续阅读，状态较平稳"

## 6. 结果回写 L0 语义缓存

### 6.1 视觉事件包装

**处理流程**：
1. 文本向量化：将视觉事件描述转换为 384 维 embedding
2. 包装为 CacheRecord：`[视觉事件] + 事件描述 + VLM 分析结果`
3. 写入 Redis + SQLite：使用现有 L0 缓存基础设施
4. 注入对话上下文：作为 AgentEvent 送入 AgentLoop

### 6.2 信号分流策略

| 用途 | 信号类型 | 注入方式 | 置信度阈值 |
|------|---------|---------|-----------|
| **短期上下文提示** | 用户抬头、微笑、离开返回 | 注入主 LLM 当前轮次 | >0.7 |
| **情绪弱刺激** | 表情变化 → valence/arousal 微调 | 注入情绪状态机 | >0.8 |
| **长期观察** | 稳定行为模式、高显著事件 | 压缩后写入 L3/L4 记忆 | >0.85 |
| **L0 缓存** | 所有视觉事件 | 写入语义缓存 | >0.6 |

## 7. 性能指标与优化

### 7.1 端到端延迟分解

```text
WebSocket 接收帧        ~5 ms
  ↓
MOG2 背景减除          ~1-3 ms
  ↓
三信号融合             ~0.1 ms
  ↓
峰值检测 + 清晰度优选   ~0.5 ms
  ↓
VLM 推理 (批量)        ~500-2000 ms  ← 主要瓶颈
  ↓
文本向量化             ~4 ms
  ↓
L0 缓存写入            ~1 ms
  ↓
总计                   ~512-2010 ms
```

**优化策略**：
- 本地处理总计 ~10 ms，远低于 30fps 的 33ms 帧间隔，不构成瓶颈
- VLM 批量推理（batch=4-8）可将单帧延迟从 2s 降至 0.5s
- 异步化 VLM 调用，不阻塞帧检测线程

### 7.2 吞吐量与并发

| 指标 | 值 | 说明 |
|------|-----|------|
| **WebSocket 连接数** | 100-500 | 单实例支持 |
| **帧处理吞吐量** | 1000 fps | 全局计算线程池 |
| **VLM 调用频率** | 2 次/分钟/用户 | 成本控制 |
| **L0 缓存写入** | 1000 QPS | Redis RPUSH |
| **内存占用** | ~2 GB | 包含 OpenCV + ONNX Runtime |

### 7.3 资源配置建议

**单实例规格**：
- CPU：16 核心（8 核 IO + 8 核计算）
- 内存：4 GB（模型 + 帧缓冲 + 计算线程池）
- GPU：可选（CUDA 加速 VLM 推理）
- 网络：千兆网卡

**扩展策略**：
- 水平扩展：Nginx 负载均衡 + 多实例部署
- 垂直扩展：增加计算线程池大小
- GPU 加速：CUDA VLM 推理可提升 5-10x

## 8. 流媒体传输层技术选型

### 8.1 WebSocket vs GStreamer

**当前方案：WebSocket + OpenCV**

| 特性 | WebSocket | GStreamer |
|------|-----------|-----------|
| **实现状态** | ✅ 已完备实现 | ⏸️ 依赖已引入，未封装 |
| **复杂度** | 低（协议简单） | 高（pipeline 配置） |
| **适用场景** | 教育场景低码率流 | 专业流媒体处理 |
| **编解码** | OpenCV 手动解码 | 内置硬件加速解码 |
| **容错能力** | 基础（重连机制） | 强（自适应码率、丢包恢复） |
| **扩展性** | 有限（单一格式） | 强（多路流、转码、录制） |
| **性能开销** | 低（轻量级） | 中（pipeline 开销） |

**选型理由**：
- **Phase 1（当前）**：WebSocket 足够满足教育场景需求
  - 摄像头低码率流（720p @ 15-30fps）
  - 已有完备的 Boost.Beast 实现
  - 与现有 HTTP 服务器共享基础设施
  - 快速验证整个视觉感知流程

- **Phase 2（未来优化）**：引入 GStreamer 的触发条件
  - 需要硬件加速解码（NVDEC/VAAPI）降低 CPU 占用
  - 需要处理多路流（多摄像头、屏幕共享）
  - 需要转码或录制功能
  - 需要更强的容错能力（网络抖动、丢包恢复）

**混合方案（可选）**：
- WebSocket 做传输层（保持现有实现）
- GStreamer 做解码和预处理（通过 appsrc/appsink 桥接）
- 优势：复用 WebSocket 连接池，获得 GStreamer 解码能力

### 8.2 解码性能对比

| 解码方案 | CPU 占用 | 延迟 | 硬件加速 | 实现复杂度 |
|---------|---------|------|---------|-----------|
| **OpenCV (软解)** | 中等 | 5-10 ms | ❌ | 低 |
| **GStreamer (软解)** | 中等 | 3-8 ms | ❌ | 中 |
| **GStreamer (NVDEC)** | 低 | 2-5 ms | ✅ GPU | 中 |
| **GStreamer (VAAPI)** | 低 | 2-5 ms | ✅ Intel iGPU | 中 |

**当前选择**：OpenCV 软解，单实例可支持 100-500 并发连接，满足初期需求。

## 10. 与主系统集成

### 10.1 集成路径

**第一阶段（MVP）**：
- 视觉结果作为 AgentEvent 送入 AgentLoop
- 不改动主对话链路，最低风险

**第二阶段**：
- 高置信视觉信号注入情绪状态机
- 微笑 → valence +0.15，皱眉 → valence -0.1

**第三阶段**：
- 压缩后的视觉观察写入 L3/L4 长期记忆
- 只写入稳定行为模式或高情绪显著事件

### 10.2 服务端口规划

| 服务 | 端口 | 协议 | 说明 |
|------|------|------|------|
| Streaming Gateway | 8081 | WebSocket | 流媒体专用入口 |
| VLM Inference | 50056 | gRPC | 视觉推理服务 |
| Visual Event Writer | 内部 | - | 结果回写 L0 |

## 11. 故障隔离与降级

| 故障场景 | 影响范围 | 降级策略 |
|---------|---------|---------|
| **VLM 服务不可用** | 视觉事件无语义解释 | 只记录原始帧元数据，不注入对话 |
| **计算线程池满** | 帧处理延迟增加 | 丢弃低优先级帧，保证实时性 |
| **Redis 不可用** | L0 缓存写入失败 | 降级到本地内存缓存 |
| **WebSocket 连接断开** | 单用户流中断 | 自动重连，恢复流式传输 |
| **OpenCV 崩溃** | 帧处理失败 | 跳过当前帧，继续处理下一帧 |

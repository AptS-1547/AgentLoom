## 🏗️ 架构概览

```
客户端 → Nginx → C++ 网关 → ┬→ C++ 人格服务
                            ├→ C++ 推理服务
                            ├→ Python 视觉服务（小橘）
                            ├→ Python 记忆服务（小橘）
                            └→ Python RAG 服务
```

**核心设计原则**：
1. **故障隔离**：gRPC 隔离各服务，单点崩溃不影响整体
2. **性能优先**：热路径（高频）用 C++，冷路径（低频）用 Python
3. **快速迭代**：业务逻辑密集模块保留 Python
4. **水平扩展**：各服务独立部署，可按需扩展

## 🛡️ 故障隔离策略

| 服务崩溃 | 影响范围 | 降级策略 |
|---------|---------|---------|
| **推理服务** | 当前请求失败 | 返回缓存结果或"系统繁忙" |
| **人格服务** | 当前请求使用默认情绪 | 使用 baseline 情绪和通用 Prompt |
| **视觉服务** | 视觉分析失败 | 跳过视觉信息，只用文本 |
| **记忆服务** | 记忆压缩失败 | 只用 L1 缓存，不压缩 |
| **RAG 服务** | 不注入知识库 | Prompt 中不包含 RAG 内容 |
| **网关服务** | 整个系统不可用 | 多实例部署 + Nginx 负载均衡 |

**关键优势**：通过 gRPC 隔离，推理服务 CUDA OOM 不会导致整个系统崩溃。

## 🎓 关键决策点

### 为什么选择微服务架构？
1. **故障隔离**：推理服务崩溃不影响其他服务
2. **独立部署**：可以单独更新推理模型
3. **水平扩展**：各服务独立扩展
4. **技术栈灵活**：C++ 和 Python 各司其职

### 为什么不嵌入 Python？
- **故障传递**：C++ crash 会导致整个进程崩溃
- **调试困难**：跨语言调用栈难以追踪
- **部署复杂**：需要带完整 Python 环境

### 为什么不全 C++？
- **开发效率**：记忆压缩、RAG 等业务逻辑用 Python 快 5 倍
- **快速迭代**：甲方需求变化时，Python 改动更快
- **生态成熟**：LangChain、向量数据库等 Python 生态更完善

### 为什么复用小橘？
- **视觉链路已验证**：`VisualPerceptionPipeline` 已通过端到端测试
- **记忆系统更完善**：包含遗忘曲线，比教育版更成熟
- **多模态能力**：音频、语音识别是增值功能
